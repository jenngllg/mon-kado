# In-app notifications

The header bell sits beside Account on desktop. On mobile and tablet it remains visible outside the collapsed navigation, between member search and the menu button; opening notifications closes that navigation. Its dot means there are unread, currently authorized notifications; it has no counter. The bell opens a panel without leaving the current screen, listing newest activity first with 20 items per page. The legacy `/notifications` address opens this panel through a guarded redirect. Opening an item marks it as read and opens its destination. “Tout marquer comme lu” applies to all currently visible pages. Read state is stored in PostgreSQL and shared across sessions.

| Event | Recipients and destination |
| --- | --- |
| Wishes added | Existing followers only, opening the followed list through its original public or private group grant. Unread additions to the same list within five minutes are grouped without delaying the first notification. Following does not replay past additions. |
| Group joined | Other current members, opening the group. Both named invitation acceptance and admission codes are supported. |
| Group invitation | Its recipient, opening Groups to accept or decline. Expired, revoked or consumed invitations are hidden. |
| Occasion reminder | Followers, at seven days and one day before the list's calendar date. UTC dates are used without inventing annual recurrence. Lists from the same owner, occasion and date share one reminder per recipient and threshold. |
| Sharing reminder | The owner, once after 48 hours, only for an active nonempty list with neither a public link nor group sharing. “Garder pour moi” permanently dismisses it for that list. |
| List shared in a group | Other members, opening that group's list. Covers explicit sharing and visibility acquired by enabling public sharing. |
| Reserved wish removed | The reserving registered member, opening their reservation history. The notification uses their own retained history. |
| Wish reserved | The owner, only when surprise mode is disabled at reservation time. Includes the current displayed participant name, including a confirmed guest's name, and the wish. Self-reservations do not notify their author. Cancelled reservations are hidden. |
| Private suggestion added | Other eligible members of its original group, opening the private suggestion. The beneficiary and author never receive it. |

## Privacy and delivery

Actions and their notifications commit in the same transaction. UUID v7 identifiers are generated by the application. Notification records reference their original follow, invitation, participant, group and list rather than persisting public sharing secrets or private message snapshots. Reads, unread status, read commands and destination resolution use the same server-side live authorization predicate. Turning on surprise mode hides previous reservation notifications and excludes them from the dot; switching it off does not create notifications for reservations made while surprise mode was enabled.

PostgreSQL `NOTIFY` publishes committed invalidations without payload. One `LISTEN` connection per API process serves bounded authenticated SSE connections. The browser uses its normal session transport and headers; no credentials are put in an event URL. Session validity and active impersonation authorization are rechecked before disclosure and during heartbeats. Reconnection reads the current unread state, recovering activity missed during an interruption. Only notifications synchronize in the background; other business views retain their manual refresh policy. The notification panel reauthorizes its contents on invalidation and restores keyboard focus when the focused item still exists.

The worker produces time-based reminders in bounded batches under a PostgreSQL advisory transaction lock; duplicate suppression is enforced in the database. Its normal `WORKER_INTERVAL` controls scheduling precision (10 seconds by default). No email, browser push permission, paid service or external network provider is involved. Existing eligible lists can receive their first reminder after the feature is enabled.

Exports include the member's currently authorized in-app notification identifiers, kinds, counts and read timestamps. They exclude share capabilities and hidden reservation/suggestion data. Account deletion cascades the member's notifications.

## Configuration

All options are validated before startup. `JOB_BATCH_SIZE` also bounds each reminder category's scheduler pass.

| Variable | Default |
| --- | --- |
| `NOTIFICATION_MAXIMUM_STREAMS` | `256` per API process |
| `NOTIFICATION_HEARTBEAT_INTERVAL` | `20s` |
| `NOTIFICATION_WRITE_TIMEOUT` | `5s` |
| `NOTIFICATION_RECONNECT_DELAY` | `1s` for the PostgreSQL listener |
| `NOTIFICATION_GROUPING_WINDOW` | `5m` |
| `NOTIFICATION_SHARING_REMINDER_DELAY` | `48h` |

## Run, verify and roll back

From the backend repository, run `./scripts/Build-Native.ps1`, then apply migration `027_member_notifications.sql` explicitly with `go run ./cmd/migrate` in the configured native environment. Start the API and worker with `./scripts/Start-Native.ps1 -Service api` and `./scripts/Start-Native.ps1 -Service worker` in separate terminals. Run `pnpm dev` from the sibling frontend repository. Reuse existing processes when available; restart them after rebuilding. The earlier local prototype numbered this migration 029; production retains its existing 001–026 catalog and appends 027 without rewriting any historical migration.

Run `./scripts/Test-Native.ps1 -Coverage` for backend contracts against the isolated native PostgreSQL test database. Frontend checks are `pnpm typecheck`, `pnpm lint`, `pnpm test:coverage`, `pnpm build` and `pnpm exec playwright test e2e/notifications.spec.js`. Browser tests use controlled API responses; the local acceptance check also exercises real API sessions, persistence, live delivery and surprise-mode changes together.

Production uses the existing deployment and verified encrypted off-VPS backup procedure. This feature's migration is additive. Rollback restores the previous API, worker and frontend artifacts together and leaves the new table, column and read state intact; the old application ignores them. Do not drop notification data or reverse the migration as part of a routine artifact rollback. Restore persistent data only through the project's documented restoration procedure when necessary.
