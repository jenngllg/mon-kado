# MK-938 local release-quality validation — 2026-09-26

## Image memory remains a publication blocker

The baseline and the initial allocation optimization below both fail the
existing 40 MP PNG gift-image case, with **one upload**, one OOM kill and no
automatic restart. This is a failed scenario, not a successful benchmark with
missing samples. The associated JSON preserves exact revisions, container image
IDs, effective limits, data invariants and failed sub-step.

| Run | Revision | Completed background requests | Unexpected errors | OOM kills |
|---|---|---:|---:|---:|
| `mk816-e5cfcac066e5` baseline | `68b25f034bbec5b219a8cd1bd5a4052158397fb8` | 163 / 9000 | 33 | 1 |
| `mk816-dc1785cd62cf` optimized | `2e318fd5bff1c8ef5386d6f730ac84b56cdf2d63` | 113 / 9000 | 43 | 1 |

Both runs used a verified shared 805,306,368-byte (768 MiB) cgroup, no swap,
one logical CPU, the same deterministic dataset and ten genuine Docker source
addresses. The local Docker Desktop engine has 12 CPUs and 8,286,515,200 bytes
of memory; the generators are outside the application budget. API is Production,
Worker is Local with external providers disabled. No production data, secret,
Drive repository or VPS connection was used.

Before the failure, all twelve normal/near-byte-limit gift/profile checks
completed: approximately 2 MP and 10,262,753-byte PNGs, one upload followed by
two concurrent uploads. Output retrieval/integrity checks passed. The later
40 MP profile and concurrent 40 MP cases were **not reached**. They must not be
reported as validated. This run order and every threshold are unchanged.

The optimization reuses the validated codec, requests supported sampled sizes,
preserves output dimensions calculated from the original image, uses normalized
four-byte pixels and releases source buffers before WebP encoding. Unit tests
verify actual JPEG/WebP reduced decoding, PNG full-size decoding, cancellation,
ownership and existing image behavior. **It does not eliminate the demonstrated
PNG memory failure.** No admission rejection, queue, pixel-limit reduction,
forced collection, dependency replacement or VPS resize was introduced.

Both runs exhausted the cgroup budget before the kernel killed the API.
The old report summary only included successful periodic observations and
therefore understated that final peak (729,153,536 and 670,277,632 bytes). The
terminal infrastructure observation records 805,306,368 bytes for the baseline
and 805,310,464 bytes for the optimized run, against a limit of 805,306,368 bytes.
MK-938 additionally fixes this reporting defect and tests that terminal
OOM evidence cannot be lost; CPU averages still exclude post-stop time. Original
raw reports remain unchanged locally, and the compact evidence retains both
peak fields so the discrepancy is explicit.

The failed runs were stopped without retry. Only their labelled Docker
containers, networks, volumes and dedicated cgroups were removed; local evidence
remains. Data checks after failure retained 100 members, 500 lists, 10,000 wishes,
202 images after fixture writes and no over-reserved wishes. This is not a
guarantee against data loss for untested failures.

## Nominal throughput evidence is not yet qualified

Run `mk816-a09f98141ffd` on clean revision
`32034caf75cdfcb0019d839350c9735dc1fa7fd3` completed all 9,000 business
requests, with no unexpected errors, 429s, dropped iterations, OOM kills or
restarts. Read p95 values were 6.18 / 9.09 / 18.71 ms (lists / wishes / shared),
and write p95 values were 19.02 / 100.53 ms (update / reservation). The verified
budget was unchanged. The memory peak was 502,181,888 bytes; mean measured CPU
was 10.71% of one core. Dataset invariants remained intact.

However, completion timestamps span **923.36 seconds**, with an observed rate
of **9.746 requests/second**, not ten. All ten shards individually span about
923.09 seconds for 900 requests; this is not merely staggered generator startup.
The cause of the time discrepancy is not established. It must not be silently
attributed to the application, ignored as clock noise, or labelled qualified.

The original automatic verdict was `passed`: it required the complete request
count but divided that count by the *planned* duration without gating the
observed rate. MK-938 fixes this second reporting defect. Every performance-profile
stage now requires complete timestamps and an observed completion rate at least equal
to its requested rate; only numerical floating-point rounding is tolerated.
The stress stages are checked separately so a faster stage cannot hide a slower
one. Missing timestamps or clock discontinuities cannot establish throughput.
The original evidence is retained, and a corrected verdict is explicitly a
reassessment of those same samples, not a new execution or a successful rerun.

Unit tests cover complete-but-slow work, the exact numeric boundary, missing or
zero-span timings, and an overall fast stress campaign with one slow stage.
The deterministic Python tests retain 100% statement and branch coverage.
No requested rates, durations, resource limits or application contracts changed.

An independent network-free Docker clock probe subsequently measured
50.000076536 monotonic seconds against 51.684444427 civil-clock seconds
(a 1.684367891-second difference). A clock discrepancy is therefore directly
observed in this environment. It can affect timestamp-derived throughput and
CPU averages; do not retrospectively rescale measurements or blame API capacity
based on this result. No host or VM clock setting was changed.

## Follow-up native-copy correction awaiting the image campaign

Review of the pinned SkiaSharp 4.152.1 implementation found that `DrawBitmap`
converts the bitmap with `SKImage.FromBitmap`. Decoding leaves its source bitmap
mutable. [Skia documents that immutable, shareable pixels can be reused instead
of copied](https://api.skia.org/namespaceSkImages.html). The decoded bitmap is
now marked immutable once decoding has finished and cancellation is checked;
the pipeline never modifies those pixels afterward.

The existing six JPEG/WebP/PNG gift/profile unit cases additionally compare the
native pixel addresses through that same image conversion before drawing.
They confirm sharing, rather than merely checking the immutable flag. The 82
local image tests pass (two unrelated Windows platform skips), and the processor
retains 242/242 sequence points and 70/70 branches covered. No decoder change,
new admission behavior or resource increase is involved. A fresh image campaign
will verify the effect after the currently running sequential campaigns. The
earlier OOM evidence remains unchanged; this unit-level proof does not by itself
resolve the publication blocker.

## Functional CI smoke is not the local performance qualification

CI run `36250890513` retained a failed smoke artifact (`mk816-07c482767c51`):
300/300 requests completed, no errors, 429s, drops, OOM kills or restarts, and
all ten generators exited successfully. Its completion span was 30.640191 seconds
and its observed rate was 9.758425 requests/second. The newly added throughput
gate had incorrectly applied the performance criterion to this short shared-runner
smoke, despite the plan explicitly excluding runner speed as a VPS reference.

The scope regression is corrected without relaxing any local nominal threshold:
reports now explicitly identify `functional-smoke` versus `local-performance`
and whether throughput qualification is required. Smoke still requires complete
work, timestamps, successful functional responses, no dropped iterations and
verified stable resources, while recording its actual throughput even when below
target. Every non-smoke profile retains the observed-rate gate. The failed CI
artifact is retained as historical evidence, not relabelled as a fresh pass.
The 59 Python tests cover this distinction at 100% statements and branches.

## Release decision

Do not certify the complete performance target or close the lot as technically
green while this memory failure remains. The user chose to retain the current
HTTP behavior rather than add an admission limit. A different decoder strategy
or another scope/resource/contract decision requires separate approval; no such
change is hidden in this MR. No production merge or deployment is authorized by
these local tests. Remaining campaign and final CI evidence will be recorded
separately as it completes.
