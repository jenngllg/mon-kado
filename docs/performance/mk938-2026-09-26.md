## Follow-up: explicitly approved bounded image admission

After the concurrent PNG failure, the owner approved serializing image uploads
with bounded waiting. Gift/profile uploads and merchant import previews share **one process-wide
permit**, a **FIFO queue of two**, and a **five-second maximum admission wait**.
These conservative limits are fixed for the existing 768 MiB application budget;
there is no new production setting that can silently increase concurrency.

Admission follows validated Bearer identity and the existing request/business
quotas, but precedes request-body buffering and MVC multipart binding. The lease
covers the complete downstream upload, including decoding, encoding and storage,
and is released on success, exception or cancellation. An admitted upload is not
cancelled when its former queue deadline passes. Missing or invalid Bearer
credentials do not occupy the queue. Reads, deletes and other endpoints do not
use it. Merchant previews hold the same permit during their bounded download
and optional image normalization, preventing a third decoding path from bypassing
admission. No external provider was enabled for validation. This is per API
process, not distributed admission or DDoS protection;
slow uploads can occupy the permit subject to the existing server timeouts.

A full queue or expired wait returns the existing `429 ErrorResponse` with
`REQUEST_RATE_LIMIT_EXCEEDED`, `Cache-Control: no-store` and a conservative
`Retry-After: 60`. No automatic client retry is introduced. Waiting requests do
not pre-buffer their full bodies. Existing 10 MiB / 40 MP image limits and
business quotas are unchanged, as are the VPS resources and external providers.

The previous failures below remain historical evidence. The fresh image campaign
described below exercises this follow-up; it does not resolve the independent
timing or publication prerequisites, nor establish spare memory capacity.

The first admission attempt, `mk816-73b25a8c4e90` at `dd7c3e5`, failed during
fixture preparation: ten parallel k6 setups overwhelmed the intentional queue.
Seven generators exited with setup failure; the three remaining generators
were explicitly stopped before measurement. No 40 MP case was reached, no OOM
occurred, and no memory qualification is claimed. Its metadata truthfully records
a dirty checkout containing only test-helper edits, outside the Dockerfile's
build inputs. Original local reports are retained.

The harness now prepares and verifies the same 200 images sequentially through
real HTTPS before generators start. Ten preparation helpers have distinct private
Docker IPs and run one at a time, outside the application cgroup. All existing
login/upload quotas remain enabled. Rejections fail preparation immediately;
there is no automatic retry. k6 retains ten simultaneous source IPs, its original
arrival rates, warmup, durations and thresholds. Preparation is not part of the
measured load. This adaptation does not turn overload rejection into a successful
measurement or hide the first failed attempt.

## Follow-up native-copy correction: single image fixed, concurrent OOM remains

Review of the pinned SkiaSharp 4.152.1 implementation found that `DrawBitmap`
converts the bitmap with `SKImage.FromBitmap`. Decoding leaves its source bitmap
mutable. [Skia documents that immutable, shareable pixels can be reused instead
of copied](https://api.skia.org/namespaceSkImages.html). The decoded bitmap is
now marked immutable once decoding has finished and cancellation is checked;
the pipeline never modifies those pixels afterward.

The existing six JPEG/WebP/PNG gift/profile unit cases additionally compare the
native pixel addresses through that same image conversion before drawing.
They confirm sharing, rather than merely checking the immutable flag. The 82
local image tests pass (two unrelated Windows platform skips), and the processor
retains 242/242 sequence points and 70/70 branches covered. No decoder change,
new admission behavior or resource increase is involved.

arrival scheduling at that boundary. Commit `9ca1289` adds an instantaneous
transition to zero followed by a one-second zero-arrival tail. This gives the
last scheduled arrival time to start, without extending any measured stage,
requesting extra business operations or changing the existing 15-second
in-flight grace period. The four 300-second stages, rates 5/10/20/5 and exact
12,000-request requirement are unchanged. The business guard still refuses
operations beyond the planned count.

`9ca12892b5ed028b659de2d4315765f84056c00f`, verifies **12,000/12,000**
business requests and ten successful generator exits. Each stage is complete
